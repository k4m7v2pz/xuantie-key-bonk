# 交接：新建独立工程目录内渲染库音频初始化失败

> 转交对象：「玄铁工具链」/「玄铁语言维护」对话。本仓库（xuantie-key-bonk）对话只负责业务重写，不在此深挖 xtc/链接层。
> 提出日期：2026-10-19。环境：macOS arm64（Darwin / Apple Silicon），xtc 懒加载预编译二进制，miniaudio + Core Audio 后端。

## 1. 现象

同一份纯渲染库探针（不经过音频封装库），在**不同目录**结果相反：

- **成功**：在 `~/Documents/Code.localized/xuantie-audio-player` 原工程目录运行，打印 `Device initialized successfully`（miniaudio | Core Audio，48000Hz 立体声），`R.合成音效(440,300)` 返回句柄 1，`播音效`、`关闭音频()` 均正常。
- **失败**：在新建的独立目录（干净骨架，或把音频库工程**完整复刻**过去）运行同一探针，打印：
  ```
  WARNING: AUDIO: Failed to initialize playback device
  WARNING: SOUND: Failed to get frame count for format conversion
  WARNING: AUDIO: Failed to create data conversion pipeline
  WARNING: SOUND: Failed to create buffer
  合成句柄=0
  WARNING: AUDIO: Device could not be closed, not currently initialized
  ```
  退出码仍为 0，但设备从未初始化、句柄为 0。

系统音频本身健康：失败后立刻回原工程目录复跑探针，依旧成功，排除设备被占用或全局音频故障。

## 2. 最小探针（两处共用，逐字相同）

```
引 "渲染" 予 R
R.初始化音频()
设 s = R.合成音效(440, 300)
示("句柄=" & 字(s))
若 s != 0 { R.播音效(s); 时.睡(400) }
R.关闭音频()
```

成功侧：在 `xuantie-audio-player/` 内 `xtl run 探针.xt`。
失败侧：任一新建目录放上述探针 + 渲染依赖，`xtl run 探针.xt`。

## 3. 已逐项排除（勿重复查）

- raylib 静态库：两边 `libraylib.darwin-arm64.a`、`libraylib.a` 的 sha256 一致。
- 桥接代码 / 渲染.xt：换用音频库自带桥、换回内置 add 桥，结果不变。
- `xtl.json`：用音频库原版对齐（依赖仅 `渲染:内置:核心库`），失败依旧。
- `xtl.lock`：补/换音频库的 darwin-arm64 二进制指纹段（下载地址+sha256），失败依旧。
- 编译缓存：`xtl clean --all` 清掉产物与 tiepm_modules 后重加依赖，失败依旧。
- 是否 git 仓库：新目录 `git init` 与否都失败；与上级是否 git 仓库无关。
- 目录层级/上级仓库：放到仓库外的干净独立目录也失败。
- 完整复刻：把音频库工程全部非隐藏文件复制到新目录，仍失败。

## 4. 请接手方排查的方向

1. **链接期选库/选桥**：新目录首次构建时，xtc 是否把 `渲染桥.c` 编进桥目标、是否链入 `libraylib.darwin-arm64.a`（含 miniaudio/Core Audio）；是否只在"特定工程形态"下才链音频后端。可对比成功目录与失败目录实际链接命令里的桥目标与 `.a`。
2. **InitAudioDevice 失败分支**：miniaudio `Failed to initialize playback device` 在本环境的触发条件；是否缺前置（图形/窗口上下文、工作目录资源）导致设备初始化被静默跳过。
3. **裸包名 `引 "渲染"` 解析落点**：新目录解析到的渲染是自带库 `lib/渲染`、铁铺 `~/.tiepm/已安装/渲染`，还是项目 `tiepm_modules/渲染`；三处副本的音频初始化行为是否一致。
4. 成功工程 `xuantie-audio-player` 与失败工程的 `xtl run` 实际编译/链接命令差异（建议加详细日志打印对比）。
